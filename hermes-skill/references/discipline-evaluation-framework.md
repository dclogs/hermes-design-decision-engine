# 学科框架扩展方法论

记录本次会话中使用的系统性学科评估流程。用于未来评估是否向框架中添加新学科。

## 三个核心问题

评估一个新学科之前，先回答三个问题：

```
① 这个学科是否带来现有框架无法覆盖的视角？
② 这个学科的洞察能否转化为可执行的流程检查/自检项？
③ 这个学科的加入是否会显著提升最终输出的品质？
```

任一"否" → 不加入。

## 重叠度评估量表

| 重叠度 | 含义 | 决策 |
|--------|------|------|
| **极高** | 已被现有某个学科完全覆盖，被覆盖方无增量 | ❌ 不加入，不吸收 |
| **高** | 绝大部分内容已被覆盖，仅极少数独特洞察 | ❌ 不加入，独特洞察吸收到对应 reference |
| **中高** | 核心概念重叠但视角不同，有少量增量 | ❌ 不加入，增量内容吸收到对应 reference |
| **中** | 部分重叠，但有明确独特的分析框架 | ⚠️ 吸收到现有 reference，不独立成学科 |
| **中低** | 少部分重叠，大部分是新的 | ✅ 考虑新增为轻量级学科，或吸收后保留 |
| **低** | 几乎不重叠 | ✅ 独立评估是否需要新增为学科 |

### 快速排除条件

以下情况直接排除，不需要完整评估：
- 该学科的所有洞察已经被另一学科'不费力地'覆盖（如 可用性工程→体验设计）
- 该学科的洞察无法转化为 agent 可执行的检查项（纯思辨性学科，如纯哲学美学）
- 该学科只对极少数输出场景有用（如建筑学只对页面布局有极微小的增量）

## 吸收 vs 新增决策树

```
新学科评估开始
├─ 与现有框架重叠度 ≥ 中高？
│   ├─ 是 → 能否吸收到现有某个 reference 文件？
│   │   ├─ 是 → 吸收（写 1-2 个小节到对应文件）
│   │   └─ 否 → 不加入，记录原因到输出跟踪
│   └─ 否（重叠中低或低）
│       ├─ 能否转化为 ≤3 条自检项？
│       │   ├─ 是 → 轻量加入（框架表 1 行 + 润色/自检各 1 项）
│       │   └─ 否 → 完整加入（框架表 1 行 + reference 文件 + 流程节点 + 自检项 + 陷阱）
│       └─ （需要一个完整 reference 吗？）
│           ├─ 是 → 写 reference（遵循信息架构原则）
│           └─ 否 → 框架表+自检即可
└─ 决定后：更新预加载清单 + 文件计数
```

## 评估检查清单

```
□ 该学科与现有 10 个学科逐一比对（不只看名字，看字段体现和可检查项）
□ 填写重叠度表（极高→低选一）
□ 如果吸收：确定吸收到的目标 reference 文件
□ 如果新增：确定框架表行 + 流程节点 + 润色/自检 + 陷阱
□ 更新预加载清单（加入 OPTIONAL 或 RARE）
□ 更新 reference 文件计数
```

## 架构评审分类法（ChatGPT 评审后补充）

评审一个新学科或架构问题时，先按以下标准分类：

### 第一类：影响 Agent 行为（必须改）

修改会改变 agent 在流程中的判断标准、执行顺序或输出质量。

典型特征：
- 涉及 if/else 分支、检查项、输出结构、颜色/字体/布局的推导逻辑
- 删除后 agent 会做出不同的决策

举例：SCQA 强套对比表（agent 会多写一段废话）、Fallback 条件不全（agent 会漏触发）

**处理方式：** 优先改。写进流程代码和自检清单。

### 第二类：影响可理解性（应该改）

修改不会改变 agent 行为，但会让人类读起来更清晰。

典型特征：
- 涉及命名、分组、注释、模块划分
- 删除后 agent 行为不变，但人维护时更容易出错

举例：IA/金字塔是否出现在框架表（人看了清楚，agent 不受影响）

**处理方式：** 新增小节/注释/分组标签，不改流程逻辑。

### 第三类：作者视角（文档清理）

只对 skill 作者有意义，agent 完全不用的内容。

典型特征：
- 不参与决策、不参与路由、不参与验证
- 纯解释性、纯元数据

举例：框架表第 4 列"对应原理角色"、废弃的 reference

**处理方式：** 删。Agent 不用 = 删。

## 迭代方向诊断：流程问题 vs 经验问题

在评估"是否要改 skill 本身"之前，先分类问题的根因。

### 流程问题（Process Issue）

特征：agent 按当前规则执行时必然产生的结果——即使有全部领域知识，流程本身就有盲区。

处理方式：立即修复。加规则、加检查、加流程节点。

| 类型 | 典型例子 | 修复方式 |
|------|---------|---------|
| 调研维度缺失 | 只搜了厂商+行业，没搜客户 | 2A 增加调研维度约束（Supply/Demand/Market） |
| 结论无约束 | 核心发现没有数据支撑 | 增加三要素约束（数据+来源+推理链）+ Novelty Check |
| 建议不突出 | 分析偏 research 非 executive | Recommendation 结构化（时间轴+优先级+No-Regret Move） |
| 验证不完整 | 检查散落多处无总闸门 | 增加 2E+ 最终验证 |

### 经验问题（Experience Issue）

特征：agent 按规则执行了，但因为缺乏行业知识，产出的结论像"常识"而非"洞察"。

处理方式：不能通过加规则解决。通过 output-tracker 的 insight_quality 积累用户的纠正，每 20 条做一次根因分析。

| 典型表现 | 例子 | 积累路径 |
|---------|------|---------|
| 核心发现是行业共识 | "数字化转型是趋势" | output-tracker 记录为 C 级 |
| 建议太泛 | "加强AI投入" | 仍需用户反馈"不够具体" |
| 数据虽全但无新视角 | 结论读者读前已经知道 | insight_quality 长期 C 级→触发调研策略调整 |

### 诊断流程

```
发现问题
├─ 按流程重新执行，结果是否不同？
│   ├─ 是 → 流程问题（加规则）
│   └─ 否 → 经验问题（加 output-tracker 积累）
├─ 给 agent 更多行业数据，结论会变深吗？
│   ├─ 是 → 经验问题（2A 调研维度或信源不对）
│   └─ 否 → 流程问题（洞察生成逻辑有问题）
└─ 用户反馈是"结构不对"还是"结论没用"？
    ├─ "结构不对" → 流程问题
    └─ "结论没用" → 经验问题
```
